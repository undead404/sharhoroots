# Sharhoroots project guidance

This repository is an Obsidian vault published with Quartz 4. It serves genealogy, lore, and history researchers focused on the territory that belonged to Sharhorod raion immediately before the 2020 administrative reform. This is a territorial scope, not a general interest in the former raion's surroundings. Areas, institutions, events, and records outside that territory are relevant only insofar as they directly document or explain the target territory or its inhabitants. People are covered when their documented actions, roles, or source appearances bear on the target territory; an unrelated external role alone is not enough (for example, merely being a judge in Mogilev does not make someone locally relevant). The only external entities to cover in their own right are record-keeping institutions (such as churches or parishes) whose documented coverage overlaps the target territory, and administrative areas whose territory included any part of it; discuss them only in relation to that overlap. Do not include unrelated external records or entities merely because they are nearby or historically interesting.

## Shared OpenCode and Codex setup

- This file is the shared project guidance for both agents. Repository skills live in `.agents/skills/`, which both OpenCode and Codex discover. Load the repository version when a global skill has the same name; if it is absent from the tool's skill catalog, read its `SKILL.md` directly. Resolve repository paths from the repository root and skill-relative resources from the skill directory.
- OpenCode invokes skills as `@skill-name`; Codex invokes them as `$skill-name`. These refer to the same instructions. Preserve explicit-only invocation settings in both the OpenCode `metadata` and Codex `agents/openai.yaml` when maintaining a skill.
- For an explicit invocation of `add-archive-case`, `article-gaps`, `edit-meaning`, `edit-wording`, `ingest-info`, or `start-task`, read and follow the matching `.opencode/commands/<name>.md` body as well as its named skill. These templates are the single source for the command workflows in both agents. Ignore OpenCode's command frontmatter in Codex, interpret `$ARGUMENTS` as the user's supplied arguments, and interpret `@skill-name` as loading that repository skill. In OpenCode use `/name`; in Codex use `$name` with the same arguments. `add-archive-case` and `start-task` have repository skill entry points for this purpose.
- `opencode.json` configures OpenCode only. Each agent uses its own model, tools, sandbox, and approval controls; a skill or command does not bypass those controls. Do not push Git changes from either agent.

## Working with the vault

- Preserve existing Markdown structure, YAML frontmatter, Obsidian wikilinks, embeds, and naming conventions. Prefer the conventions of nearby notes over introducing a new format.
- Whenever creating or editing YAML frontmatter under `content/`, load and follow the `content-frontmatter` skill. Treat its field definitions as the standard for metadata; keep optional fields optional, do not guess missing values, and do not make unrelated metadata sweeps.
- Whenever creating or editing a `Дотичні фонди` table, load and follow the `related-fonds-table` skill, regardless of which command or workflow triggered the edit.
- Whenever creating or editing a `Переписи та ревізії` section or its table, load and follow the `census-revision-table` skill, regardless of which command or workflow triggered the edit.
- Whenever creating or editing a `Дотичні справи` table, load and follow the `related-cases-table` skill, regardless of which command or workflow triggered the edit. The specialized census/revision rule takes precedence for `Переписи та ревізії` tables.
- **Language rule for `content/`:** Write all authored, reader-facing text in Ukrainian, including article prose, titles of vault notes, frontmatter descriptions, headings, captions, table text, labels, and explanations in citations. Do not switch languages even when asked to draft in another language. The sole exception is the exact title of an actual publication (including a book, article, or website), which may remain in its published language; add a Ukrainian explanation when useful. Translate or summarize quotations, archival descriptions, and other source wording in Ukrainian rather than reproducing them in another language.
- Render foreign personal and place names in Ukrainian script in `content/`: use an established Ukrainian form when one exists; otherwise transliterate/transcribe consistently without inventing an identity or silently changing a historically significant form. Do not add the original foreign spelling alongside the Ukrainian form. A foreign name may remain as part of an exact publication title under the exception above. Preserve source spellings in research records outside `content/` when needed for verification.
- Do not translate or alter literal identifiers, archival references, URLs, or machine-required syntax; these are data, not reader-facing prose. Where metadata contains free-text descriptions or labels, write them in Ukrainian.
- Before finishing any edit under `content/`, check newly written or revised reader-facing text for non-Ukrainian wording and foreign names left in non-Ukrainian script. Keep exact publication titles and literal identifiers unchanged; translate or adapt everything else.
- **Treat the user's statements as established facts.** This includes the user's own readings and transcriptions of handwritten records. Do not downgrade them to hypotheses, demand independent citations or corroboration, or call them unsupported merely because other sources have not been checked. The user's question marks and other explicit qualifications signal uncertainty: preserve them and do not resolve them by guesswork. Do not add details the user did not provide. If an outside source conflicts, report the two accounts distinctly; do not silently override or cast doubt on the user's statement. Machine-generated OCR/HTR remains machine output unless the user confirms or corrects it.
- Do not invent historical or genealogical facts, identities, dates, or source details. For claims derived from outside sources or the assistant's own inference, distinguish what a source states from interpretation, evidence-based hypotheses, and oral tradition. When direct proof is unavailable, include the strongest useful inference supported by inspected evidence in the relevant article, even if it is provisional: mark it explicitly with calibrated language such as _можливо_ or _ймовірно_, explain the evidence and reasoning, and state what remains unproven. Cite the evidence; never make an inference sound like a source's assertion. Uncertainty wording is not a substitute for evidence: if the available material supports no reasonable inference, say that the question remains open rather than speculate. This evidence standard does not override the rule for user-provided facts above.
- Treat named people in sources relevant to the target territory as valuable evidence, not as trivia subject to a notability threshold. Preserve a person's name and the source-supported local role, action, or appearance in the appropriate article even when the person is obscure or appears only once; do not omit them merely because a visit is not explicitly recorded. A documented appointment or role seated in a target settlement (for example, a volost chief in Lozova) is a reasonable basis to infer that the person was probably present there at least once, unless evidence says otherwise. State this as an inference, explain its basis, and do not imply the source explicitly records a visit. Conversely, a role entirely outside the target territory (such as a judge based in Mogilev) does not by itself establish a local connection or visit; mention that person only when their specific action materially documents the target territory or its inhabitants. Do not infer identity from a name alone.
- There is no blanket exclusion from this site's public content based solely on whether a person is living or recently deceased. People documented in relevant sources may be published under the same evidence and territorial-scope rules; do not remove or suppress a supported local mention merely to satisfy a generic living-person exclusion. If a build tool enforces such a blanket exclusion, report the conflict rather than silently changing source content or claiming the intended public build succeeded.
- Preserve citations and source links when editing claims. For claims from outside sources, if a claim cannot be verified directly, recast it as an evidence-based inference when warranted, or flag what remains unknown; do not silently strengthen or change it. Do not apply this verification requirement to facts the user states as their own; a search snippet, machine OCR result, or another page citing a source is not the same as inspecting that source.
- Never cite or link to Russian-language Wikipedia. For navigation-only links, use a confirmed Ukrainian-language Wikipedia page only when no relevant local article exists; never use any Wikipedia page as historical or genealogical evidence.
- Keep reader-facing evidence qualifications separate from research-process notes: article prose should explain what the cited evidence does and does not establish, while failed access attempts, HTTP/tool errors, and agent-environment limitations belong in the relevant `tasks/` research log, not the article. If research yields no new established fact but does support a useful inference, add that qualified inference to the target article. Leave the article unchanged only when there is no new supported fact or useful evidence-based inference to communicate.
- Keep Ukrainian-script place-name forms, historical administrative-unit names, and transliterations consistent with established Ukrainian usage and surrounding notes; do not normalize them by guesswork. For foreign personal and place names, follow the `content/` language rule above.
- Whenever creating a research-task note in `tasks/`, load and follow `create-research-task`; the calling workflow remains responsible for deciding whether a lead warrants a task.
- For requests to find and source historical facts, load the `research-facts` skill. For requests to reorganize, move, or rename vault articles, load the `curate-articles` skill.
- For requests to find or add article illustrations, load `.agents/skills/find-illustration/SKILL.md`. A valid result is «Вибачте, відповідного зображення не знайдено» after a bounded search; never force a substitute or imply that a picture never existed. Evaluate photographs visually, including photographs reproduced in books or scans: this is illustration selection and is exempt from the archival OCR/HTR visual-reading prohibition below. For settlement illustrations, only photographs dominated by churches or monasteries are reserved for those institutions' own articles; their incidental appearance in a broader view is acceptable. Mills, schools, other local buildings, landmarks, and scenes are valid illustrations even if they could have their own articles; a panorama is not required. Insert a suitable image with an honest Ukrainian caption and a precise source citation immediately after the initial prose paragraph, or immediately after the frontmatter when there is no introductory paragraph.
- For Sharhorod-area web research, always search in Ukrainian; route additional search languages by the historical period and subject: Russian for periods before 1991 and Old Believer topics; Turkish for 1672-1699; Polish for periods before 1930, Polish topics, and all Roman Catholic topics; Hebrew and Yiddish for Jewish or Judaism-related topics and any urban-life topic; German for periods 1941–1944 and topics concerning Austrian subjects or Lutheranism; Romanian for periods 1941–1944. Also infer relevant additional search languages from explicit context (for example, French for a French citizen, or Georgian/Kartvelian-language sources for a person identified as being from Sakartvelo); do not infer a person's origin from their name alone. These rules determine search coverage, not which credible and locally relevant findings may be used; apply period cutoffs to the period researched, not a source's publication date. Adapt queries to historically appropriate names, spellings, scripts, and terms, and record the queries used. Follow `research-facts` for the detailed research workflow.
- For historical or genealogical research, follow `research-facts`: check existing tasks and reusable records in `sources/` and local copies in `books/` before searching; search the web, inspect and record at least one source document, and save each worthwhile unanswered follow-up as its own atomic note in `tasks/`. A source record is a retrieval aid, not evidence: inspect the cited document and record its exact locator. Keep large or temporary downloads and command output in ignored `.agent-work/`; only intentionally retained source copies belong in ignored `books/`. Check existing tasks first; a task may target more than one article, but must have one research question and one deliverable. Task states are `queued` (not started), `in_progress` (research underway and able to proceed), `blocked` (a specific essential source/access/response is unavailable), `found` (supported findings recorded but article-worthy findings not yet applied), `done` (article-worthy findings applied and other supported findings dispositioned), `no_result` (bounded research ended without a supported finding or useful inference; this is not proof of nonexistence), and `fail` (work stopped by a technical failure, not a research conclusion). Resume a blocked task as `in_progress` once its dependency is available; use `no_result` only when no essential source remains pending and alternatives are exhausted. Reopen `no_result` only for a materially different or newly available research route; retry `fail` after addressing or working around its technical cause. For an existing research task, record supported facts and evidence-based inferences in the task (`found`), then apply them—with uncertainty and evidential limits explicit—to their target articles (`done`). Add relevant Obsidian wikilinks and bold an article's title at its natural first mention when revising its prose. When a research request concerns an existing article, update that article with supported findings and useful qualified inferences; a standalone research request with no relevant article target still does not authorize creating or revising an article unless asked.
- Use ignored `.agent-work/` as a disposable playground for exploratory work, including `curl` downloads, temporary scripts, extracted text, and command output; create subdirectories as useful. Do not put credentials, canonical notes, or reusable source copies there.
- When an article's published path changes, update `content/_redirects` and affected internal links in the same change. Preserve existing redirect entries and verify the old and new published paths; do not assume every route has the same prefix.
- Quartz builds the `content/` directory by default and ignores paths matching `private`, `templates`, `.obsidian`, and `**/*.excalidraw.md`. Keep research tasks in the repository-root `tasks/` directory, outside the published content tree; never copy them into generated site output.
- Do not edit generated output or local Obsidian workspace state as a substitute for editing its source.

## Historical administrative research reminder

- When researching late-imperial towns, market towns (містечка), burgher communities, or their relationship to volosts, consider the law of **29 April 1875 Old Style (11 May New Style)** extending the 1870 Municipal Statute to the western provinces, including Podolia: *О применении Городового положения 16 июня 1870 года к городам Западных губерний*, ПСЗРИ, second collection, vol. 50, no. 54640, pp. 462–464. This is a research lead, not evidence that any particular settlement changed administration on that date.
- The contemporary account in *Энциклопедический словарь Брокгауза и Ефрона*, vol. XX (1897), pp. 331–332, entry [«Местечки»](https://ru.wikisource.org/wiki/ЭСБЕ/Местечки), describes separate burgher communities where there were at least ten burgher households or householders, and attachment of smaller groups to another town's or market town's burgher community, or to a volost. Distinguish affiliation of burghers and their estate administration from a settlement's territorial incorporation, loss of town status, relocation of volost headquarters, or alteration of volost boundaries. Do not describe this as a universal law merging towns into neighboring volosts. The original act has not yet been inspected in this workspace research; verify its relevant provisions and settlement-specific implementation before applying it to an article claim. Later implementation may be relevant to changes recorded around 1880.

## Nysh CLI for archival research

- Treat Nysh as an opt-in specialist tool, not the default research path. For ordinary local-history, lore, and article work, follow `research-facts` and use the vault, relevant source documents, and web research without invoking Nysh. Use Nysh when the question specifically needs its archive catalogs, settlement/parish indexes, fonds descriptions, shared transcriptions, or local scan workflow, or when the user asks for it. Do not turn a general history or genealogy question into a surname search; load `find-surname` only for an explicit request to find or assess a name in a specific record. Before a Nysh lookup, check existing tasks, reusable `sources/` records, and `books/`, then load the matching specialist skill.
- For archival text reading or verification, never pass scan images, page screenshots, image crops, or other visual scan data to an LLM or use an LLM's vision to read or verify them. This also applies when a specialized skill calls for visual arbitration of OCR/HTR: use local OCR/HTR text and human review instead, and do not send those scans to subagents or other models. Visual evaluation of candidate article photographs, including photographs reproduced in books or scans, is allowed under `find-illustration`; this exception does not authorize transcribing or verifying archival text. Local OCR and locally running specialist handwriting recognition (HTR), including `nysh read` when available and appropriate, are allowed; for handwriting, use local HTR when available rather than asking an LLM to inspect the image. Follow the relevant Nysh skill and its resource, cost, and remote-work safeguards.
- If local OCR/HTR is unavailable, fails, or leaves the requested information unresolved, stop image-reading attempts and ask the user for the specific information needed. Identify each scan by case/path and filename, give the PDF page number (and printed page number if known), and name the field or passage to read (for example, a particular person's name, date, or relationship). Ask only for the data needed to answer the task, not for a vague review of the scan or a full-page transcription when a narrower question will do. The user may inspect the image; the agent must not pass it to an LLM. Treat locally extracted OCR/HTR text as machine output, not verified source text; once the user supplies or corrects a reading, treat that user-provided reading as established and preserve only uncertainty the user marks.
- Treat Nysh results as leads with explicit coverage and freshness limits, not as historical evidence. A zero from an incomplete catalog is not proof of absence. For article claims, inspect the underlying source itself and cite the exact locator, following the research rules above.
- After Nysh work produces shareable results, send them to Супряга as part of completing the task. The user has given standing authorization for these contributions; do not ask for confirmation again. Load the repository `share-case` skill, and `case-notebook` when contributing eligible notes or user-confirmed readings. Check what is already in the pool, validate each contribution with dry-run, publish new or updated text, line geometry, case metadata, and eligible notes, then verify receipt in the pool; packing alone is not completion. For queues, use the supported `--share` option after validating case metadata. Share partial results only with accurate coverage labels. Never upload scan images, private research notes, family hypotheses, credentials, or material whose sharing terms prohibit it. If nothing is eligible, do not upload; if authentication, metadata, or service errors prevent sharing, report the specific blocker and preserve the pending contribution rather than claiming success.
- Use case-download, HTR, record-ingest, sharing, cloud, or other stateful/costly workflows only when they fit the request and after following their Nysh skill; get confirmation before starting paid/remote work or publishing/sharing material outside the standing Супряга authorization above. Keep Nysh workspaces and private scan data outside this vault unless the user explicitly chooses otherwise.
- This repository is a Quartz history vault, not a Nysh family-canon site. Do not run `nysh site build` for it; its output and public-person rules do not match this project.
