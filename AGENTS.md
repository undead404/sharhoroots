# Sharhoroots project guidance

This repository is an Obsidian vault published with Quartz 4. It serves genealogy, lore, and history researchers focused on the territory that belonged to Sharhorod raion immediately before the 2020 administrative reform. This is a territorial scope, not a general interest in the former raion's surroundings. Areas, institutions, events, and records outside that territory are relevant only insofar as they directly document or explain the target territory or its inhabitants. People are covered when their documented actions, roles, or source appearances bear on the target territory; an unrelated external role alone is not enough (e.g. merely being a judge in Mogilev does not make someone locally relevant). The only external entities to cover in their own right are record-keeping institutions (such as churches or parishes) whose documented coverage overlaps the target territory, and administrative areas whose territory included any part of it; discuss them only in relation to that overlap. Do not include unrelated external records or entities merely because they are nearby or historically interesting.

## Working with the vault

- Preserve existing Markdown structure, YAML frontmatter, Obsidian wikilinks, embeds, and naming conventions. Prefer conventions of nearby notes over introducing a new format.
- **Enumeration layout:** Whenever enumerating more than three items, use a list (nested where useful), or a table when the entities have many attributes to compare. Apply this to authored vault text and agent replies. Do not pack such enumerations into prose, comma-separated sentences, or semicolon-separated list entries; use a separate item or row for each entity.
- Whenever creating or maintaining reusable external-source records, local-copy references, retained source texts, or passage inspection metadata in `sources/`, load and follow `.agents/skills/manage-sources/SKILL.md`. It owns the source-record schema and artifact provenance; `research-facts` owns historical research and interpretation. Normalize edited records incrementally and validate them with `npm run lint:sources -- --strict <record-paths>`; do not infer inspection or alter confirmed readings during migration.
- Whenever creating or editing YAML frontmatter under `content/`, load and follow the `content-frontmatter` skill. Treat its field definitions as the metadata standard; keep optional fields optional, do not guess missing values, and do not make unrelated metadata sweeps.
- Whenever creating or editing tables, load the matching skill: `related-fonds-table` for `Дотичні фонди`, `census-revision-table` for `Переписи та ревізії`, and `related-cases-table` for general `Дотичні справи` (the specialized census/revision rule takes precedence for `Переписи та ревізії`).
- **Language rule for `content/`:** Write all authored, reader-facing text in Ukrainian, including article prose, vault note titles, frontmatter descriptions, headings, captions, table text, labels, and citation explanations. Do not switch languages even when asked to draft in another language. The sole exception is the exact title of an actual publication (book, article, website), which may remain in its published language; add a Ukrainian explanation when useful. Translate or summarize quotations, archival descriptions, and other source wording in Ukrainian rather than reproducing them in another language.
- **Church naming:** Do not use «УПЦ» or «Українська православна церква» as an accepted name for the church using those designations; always refer to it as «РПЦ» or «Російська церква» in authored text and communication. «ПЦУ» and «Православна церква України» are valid names and must not be replaced. Preserve literal URLs, identifiers, and exact publication titles when required for source identification.
- Render foreign personal and place names in Ukrainian script in `content/`: use an established Ukrainian form when one exists; otherwise transliterate/transcribe consistently without inventing an identity or silently changing a historically significant form. Do not add the original foreign spelling alongside the Ukrainian form. Foreign names may remain as part of an exact publication title under the exception above. Preserve source spellings in research records outside `content/` when needed for verification.
- Do not translate or alter literal identifiers, archival references, URLs, or machine-required syntax; these are data, not reader-facing prose. Where metadata contains free-text descriptions or labels, write them in Ukrainian.
- Before finishing any edit under `content/`, check newly written or revised reader-facing text for non-Ukrainian wording and foreign names left in non-Ukrainian script. Keep exact publication titles and literal identifiers unchanged; translate or adapt everything else.
- **Treat user statements as established facts.** This includes the user's own readings and transcriptions of handwritten records. Do not downgrade them to hypotheses, demand independent citations or corroboration, or call them unsupported merely because other sources have not been checked. The user's question marks and explicit qualifications signal uncertainty: preserve them and do not resolve them by guesswork. Do not add details the user did not provide. If an outside source conflicts, report the two accounts distinctly; do not silently override or cast doubt on the user's statement. Machine OCR/HTR remains machine output unless the user confirms or corrects it.
- Do not invent historical or genealogical facts, identities, dates, or source details. For claims derived from outside sources or inference, distinguish what a source states from interpretation, evidence-based hypotheses, and oral tradition. When direct proof is unavailable, include the strongest useful inference supported by inspected evidence in the relevant article, marked explicitly with calibrated language (_можливо_, _ймовірно_), explaining the evidence and reasoning, and stating what remains unproven. Cite the evidence; never make an inference sound like a source assertion. Uncertainty wording is not a substitute for evidence: if available material supports no reasonable inference, state that the question remains open rather than speculate.
- Treat named people in sources relevant to the target territory as valuable evidence, not trivia subject to a notability threshold. Preserve a person's name and source-supported local role, action, or appearance in the appropriate article even when obscure or appearing only once; do not omit them merely because a visit is not explicitly recorded. A documented appointment or role seated in a target settlement (e.g. a volost chief in Lozova) is a reasonable basis to infer that the person was probably present there at least once, unless evidence says otherwise (state this as an inference). An external role alone (e.g. a judge based in Mogilev) does not establish a local connection or visit; mention that person only when their specific action materially documents the target territory or its inhabitants. Do not infer identity from a name alone.
- There is no blanket exclusion from this site's public content based solely on whether a person is living or recently deceased. People documented in relevant sources may be published under the same evidence and territorial-scope rules. If a build tool enforces a blanket exclusion, report the conflict rather than silently altering source content.
- Preserve citations and source links when editing claims. For claims from outside sources, recast unverified claims as evidence-based inferences when warranted, or flag what remains unknown; do not silently strengthen them.
- **Reader-facing attribution:** In `content/`, omit routine workflow credits such as «текст надано…», «читання користувача», or «читання Віталія Перегончука» when the citation already suffices. Do not mechanically replace «користувач» with a name or author link. Name the project author only when attribution clarifies an interpretation, original contribution, or reading authorship: use «В.П.» or «Віталій Перегончук» (inflected as grammar requires); link to `/author` only when useful, without repeating it routinely. Never call him «користувач» or expose the chat relationship in published text. Preserve source attribution and evidence qualifications.
- **Citations and notes:** Whenever creating or revising quotations, citations, footnotes, or notes in `content/`, load and follow `.agents/skills/citations-and-notes/SKILL.md`. Prefer Ukrainian paraphrases with precise Markdown source footnotes; use quotations only when wording matters.
- Apply the **Source credibility and replacement policy** below whenever evaluating sources or encountering links in `content/`. For navigation-only Wikipedia links, use a confirmed Ukrainian-language page only when no relevant local article exists; never use Wikipedia editorial content as historical or genealogical evidence.
- Keep reader-facing evidence qualifications separate from research-process notes: article prose explains what evidence establishes; failed access attempts, tool errors, and agent limitations belong in the relevant `tasks/` research log. Add supported qualified inferences to the target article.
- Keep Ukrainian-script place-name forms, historical administrative units, and transliterations consistent with established Ukrainian usage and surrounding notes.
- Whenever creating a research task in `tasks/`, load and follow `create-research-task`. For finding/sourcing facts, load `research-facts`. For reorganizing, moving, or renaming articles, load `curate-articles`.
- For article illustrations, load `.agents/skills/find-illustration/SKILL.md`. A valid result is «Вибачте, відповідного зображення не знайдено» after a bounded search; never force a substitute. Evaluate photographs visually (exempt from the archival OCR/HTR vision ban). Photos dominated by churches/monasteries are reserved for those institutions' own articles; incidental appearance in a wider view is acceptable. Mills, schools, landmarks, and scenes are valid illustrations. Insert suitable images with an honest Ukrainian caption and precise citation immediately after the initial prose paragraph (or frontmatter).
- Web research languages: always search in Ukrainian. Route additional search languages by period and subject: Russian for pre-1991 and Old Believers; Lithuanian for 1363-1596; Turkish for 1672-1699; Polish for pre-1930, Polish topics, and Roman Catholic; Hebrew/Yiddish for Jewish/Judaism and urban-life topics; German for 1941-1944, Austrian subjects, and Lutheranism; Romanian for 1941-1944. Infer other languages from explicit context (e.g. French for a French citizen, Kartvelian for Sakartvelo); do not infer origin from a name alone. Follow `research-facts` for details.
- For historical or genealogical research, follow `research-facts`: check existing tasks, `sources/`, and local copies in `books/` before searching. For new investigations, search the web, inspect and record at least one source document, and save worthwhile unanswered follow-ups in `tasks/`. Source records are retrieval aids, not evidence: inspect the document and record its exact locator. Keep temporary downloads and command output in ignored `.agent-work/`; retained source copies belong in ignored `books/`. Task states: `queued`, `in_progress`, `deferred`, `blocked`, `found`, `done`, `no_result`, `fail`. Use `deferred` with a timezone-explicit `not_before` for a timed retry: before that instant skip it; once due, `start-task` considers it alongside `in_progress`, before `queued`, and checks its dependency. Use `blocked` when no concrete retry time is known; resume it when its dependency is available. Neither state schedules an automatic launch. Use `no_result` only when alternatives are exhausted; retry `fail` after addressing the technical cause. Record supported facts/inferences in the task (`found`), then apply them to target articles (`done`) before setting `done`. Add wikilinks and bold the article title at its natural first mention. Standalone research without a relevant article target does not authorize creating or revising an article unless asked.
- Use ignored `.agent-work/` as a disposable playground for exploratory scripts, downloads, and output.
- When an article's published path changes, update `content/_redirects` and internal links in the same change.
- Quartz builds `content/` and ignores `private`, `templates`, `.obsidian`, `**/*.excalidraw.md`. Keep tasks in `tasks/`, outside published output. Do not edit generated output or local Obsidian workspace state.
- When choosing where information belongs, cross-referencing, or assessing extraction/merging, load and follow `.agents/skills/content-placement/SKILL.md`.

## Source credibility and replacement policy

The following publications have zero credibility as sources, regardless of author, institutional affiliation, apparent quality, or agreement with other accounts:

- Publications on `ru.wikipedia.org`, including its subdomains.
- Publications on any hostname in the `.ru` or `.su` zones.
- Publications on `familio.org`, including its subdomains.
- Publications on `beket.com.ua`, including its subdomains.
- Publications on `velikie.org`, including its subdomains.
- Anything published in Russian on or after **2014-02-20**, on any domain.

**Sole exception:** unchanged textual historical documents at least **75 years old** may be used and cited, especially scans (PDF, JPEG, and similar formats); faithful, unaltered transcriptions also qualify. Age is measured from the original document's date to the date of use, not its upload date or the period described. Establish and record the original's identity, age, locator, and reproduction fidelity under the archival-reading rules. The host's commentary gains no credibility from this exception. Everything else from these resources is a hint for further research only, never evidence. Mirroring or translating excluded material does not restore credibility; Russian-language searches remain permitted.

**Mandatory replacement tasks on encounter:** during any work, links encountered in `content/` under this policy must be scheduled for replacement through `create-research-task`, unless the document exception is established and recorded. This includes citations, navigation, tables, and image credits, even during editorial work. Unresolved publication dates or exceptions require verification/replacement tasks. A matching existing task satisfies scheduling. Do not waive this as a low-value gap or out-of-scope wording issue, silently delete supported information, or substitute an uninspected source. This does not require a vault-wide audit on every task.

For the evaluation procedure, evidence records, and replacement-task handoff, load and follow [.agents/skills/evaluate-external-source/SKILL.md](.agents/skills/evaluate-external-source/SKILL.md) whenever evaluating an external source or encountering a potentially excluded link. These mandatory rules apply even when that skill has not yet been loaded.

## Historical administrative research reminder

- When researching late-imperial towns, market towns (містечка), burgher communities, or their relationship to volosts, consider the law of **29 April 1875 Old Style (11 May New Style)** extending the 1870 Municipal Statute to western provinces, including Podolia: _О применении Городового положения 16 июня 1870 года к городам Западных губерний_, ПСЗРИ, second collection, vol. 50, no. 54640, pp. 462–464. This is a research lead, not evidence that any particular settlement changed administration on that date.
- The contemporary account in _Энциклопедический словарь Брокгауза и Ефрона_, vol. XX (1897), pp. 331–332, entry [«Местечки»](https://ru.wikisource.org/wiki/ЭСБЕ/Местечки), describes separate burgher communities (where >=10 burgher households) and attachment of smaller groups to another town's burgher community or volost. Distinguish burgher estate administration from territorial incorporation, loss of town status, or volost boundary changes. Do not describe this as a universal law merging towns into neighboring volosts. Verify provisions and settlement-specific implementation before applying claims.

## Nysh CLI for archival research

- Archival discovery & person-index research: use services in [.agents/skills/research-facts/references/search-services.md](.agents/skills/research-facts/references/search-services.md): Duck Inspector, ЦДІАК-442, UaRoots, Archival.name, JewishGen, and FamilySearch. Use specialist registry in [.agents/skills/research-facts/references/specialist-databases.md](.agents/skills/research-facts/references/specialist-databases.md) by triggers and priorities. Do not search every database or repeat searches of the same collection without cause. Reuse authenticated browser sessions and request human searches when gated. Duck Inspector returns <=50 results; record fuzziness and narrow capped searches. Use historical place names and period jurisdictions on failure. These routes supplement research and do not authorize unsolicited surname searches, account creation, payments, or archival scan reading by LLM.
- Local setup in `NYSH.md`. From this repository, run `sh scripts/nysh.sh <command>` to select the separate workspace; do not initialize a Nysh workspace inside the vault.
- Consult `shepit.poshuk` as a discovery step after checking tasks, `sources/`, and `books/` when beginning research on a settlement or fond, or an explicitly requested surname. Read `nysh share dovidka` and permissions via `sh scripts/nysh.sh share vyklyky --json`. Request dossiers: `sh scripts/nysh.sh share vyklyk shepit.poshuk --param misce="Шаргород" --param oblast="Вінницька" --json` or topical `--param q="..."`. Resolve candidates with the user if `stan: choose`. Record queries, locators, and limits; hints and summaries are leads, not evidence. Inspect underlying documents before applying findings.
- Specialist Nysh workflows remain specialist tools. Check tasks, `sources/`, and `books/`, then load the matching specialist skill. Load `find-surname` only on explicit request.
- **Archival reading depends on the script:**
  - **Cyrillic or Latin handwriting:** Never pass scan images, page screenshots, crops, or visual scan data to an LLM, and do not use LLM vision to read or verify them. This applies to visual arbitration of OCR/HTR: use local OCR/HTR text and human review instead.
  - **Other scripts (Hebrew, Yiddish, Ottoman Arabic):** LLM vision is permitted for reading and verification when reliably expected from catalog metadata, existing text, or tools (subject matter alone is not enough). Record the routing basis and limit visual reading to non-Cyrillic/non-Latin passages; crop mixed-script pages.
  - Visual evaluation of candidate article photos under `find-illustration` remains allowed. Local OCR and specialist HTR (`nysh read`) remain allowed; prefer suitable local HTR for handwriting.
- When asking the user to read Cyrillic or Latin archival text, provide automated OCR/HTR alongside the request whenever possible. Reuse existing output or run a bounded attempt under the relevant Nysh skill. For handwriting, prefer Nysh HTR over generic OCR. Include raw machine transcription labelled as unverified OCR/HTR, identifying engine/model, and preserving errors/competing readings. Ask the user to confirm/correct the needed passage. Do not ask users to transcribe other scripts; use OCR/HTR or the vision exception above.
- If local OCR/HTR is unavailable, fails, or leaves Cyrillic/Latin text unresolved after a bounded attempt, stop automated attempts and ask the user. Identify scans by case/path, filename, PDF page (and printed page if known), and name the specific field/passage. Ask only for data needed to answer the task, not a full-page transcription. Once the user supplies or confirms a reading, treat it as established.
- Treat Nysh results as leads with explicit coverage limits, not historical evidence. Inspect underlying sources and cite exact locators.
- After Nysh work produces shareable results, send them to Супряга as part of task completion (standing authorization granted). Load `share-case` (and `case-notebook` for eligible notes/readings). Check pool contents, validate contributions with dry-run, publish text, geometry, case metadata, and eligible notes, then verify receipt. Never upload scan images, private research notes, family hypotheses, credentials, or restricted material.
- Use stateful/costly workflows (case download, HTR, record ingest, cloud) only when fitting the request; obtain confirmation before paid/remote work or publishing outside standing Супряга authorization.
- Do not run `nysh site build` for this repository; Quartz builds the site.

- `npm run docs` runs Quartz build with its local preview server.
- `npm run check` runs frontmatter and source validation, tests, TypeScript checking, and repository-wide Prettier validation.
- `npm run lint:markdown` checks Markdown using `.markdownlint.jsonc`. For focused edits, use `npx markdownlint-cli2 ":path/to/note.md" ":.agents/path/to/SKILL.md"` with actual changed paths. Prefer the CLI over custom scripts; keep MD055/MD056 table rules unless changes are requested.
- `npm test` runs TypeScript tests.
- Run `npm run check` after TypeScript, formatter configuration, or code formatting changes; run `npm test` when behavior is affected. For Markdown-only prose, research logs, or agent instructions, run focused Markdown linting and applicable frontmatter/source validators instead of repository-wide Prettier.
- Distinguish Markdown lint from Prettier formatting. In markdownlint-cli2, `Summary: 0 issues in 0 files` is success. Report Prettier failures separately; do not loosen Markdown rules or reformat unrelated content.
- Do not reformat unrelated files or run `npm run format` across the repository unless explicitly requested.
